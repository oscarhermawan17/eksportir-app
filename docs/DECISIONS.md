Three states: **on**, **off** (its listings vanish from the catalog, the filters and `/products/:id`, which answers 404 — the seller still sees them with a badge, so nobody thinks their listing was deleted), and **archived** (soft delete, same effect plus hidden from the admin list). `ProductStatus` is deliberately left alone: visibility is computed from the category, so switching it back on restores every listing without touching a product row. **No delete at all** — the owner dropped it the same day, after seeing the screen. More decisive: off and archived already cover every real case and both are reversible, so a delete was a third concept to explain plus the page's only irreversible button. `ON DELETE RESTRICT` stays in the schema as a net rather than a feature. The migration moved **no data**: the FK is on the slug and the column kept the name `category`, so adding it was one `ALTER TABLE` after backfilling the nine rows. An unknown slug in `?category=` answers 200 + empty instead of 400, so a bookmarked filter URL survives a category being switched off (pinned by a test) |
| **The seller's "new product" form empties itself after a save** (bug found by the owner, fixed 2026-11-13) | Adding a product, submitting it for review and then pressing "Add product" again showed the previous product's text, its photos still attached, and both buttons stuck on "Saving…" — only a browser refresh cleared it. **The cause is Next.js 16, not our state handling:** a page you navigate away from is kept mounted and merely hidden (`display: none`, React Activity) so that going back is instant. The inputs are uncontrolled, so their DOM values survive, and `busy` was only set back to `false` in the `catch`. The fix is in `ProductForm`: after a successful create, `form.reset()`, the two radio states back to their defaults, `mediaKeys` emptied and the uploader remounted through a `key`; `setBusy(false)` moved into `finally`. Stale photo keys were the sharp end of it — `ProductMedia.r2Key` is unique, so the next product would have been refused with a bare "invalid input". Only the create form is emptied; the edit form keeps what was saved, and an edit page per product id was checked not to leak into another product's |
